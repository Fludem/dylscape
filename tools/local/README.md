# Local dev runbook

How to get from a cold machine to logged in. Everything here is local-only.

## What talks to what

```
RuneLite  ──▶  127.0.1.3:43701   RSProx proxy   (patched into the client)
               127.0.0.1:43600   RSProx HTTP    (serves rewritten javconfig + worldlist)
RSProx    ──▶  127.0.0.1:43595   RSMod game server
               127.0.0.1:8080    our static jav_config.ws + worldlist.ws
```

RSProx assigns each world a loopback address of the form
`127.<worldId>>8>.<worldId&0xFF>.<2 + targetId>`. World 1 as the first custom
target gives **127.0.1.3**. macOS only routes 127.0.0.1 by default, so that
alias must exist or the client cannot reach the proxy at all.

RSProx does **not** use port 43594 — it binds 43701 and rewrites `43594 -> 43701`
inside the client classes at launch.

## Start everything

`tools/local/dev.sh` does all four steps below in order, waiting on each before
starting the next. It is the normal way in:

```bash
./tools/local/dev.sh              # restart the whole stack (default)
./tools/local/dev.sh start        # only if nothing is running
./tools/local/dev.sh stop
./tools/local/dev.sh status
./tools/local/dev.sh restart --build   # rebuild the server first
```

It reads `port` from `.data/server.toml` rather than assuming 43595, only asks
for sudo when the loopback alias is actually missing, and stops the server by
main class -- so it also cleans up one started with `./gradlew run`. Logs land in
`tools/local/logs/`. Without `--build` it runs the existing `installDist` output,
so **a code change needs `--build`**. In IntelliJ the same four commands are the
`Dev stack [...]` run configurations.

The manual steps it automates, for reference:

```bash
# 1. loopback alias (needs sudo, does not survive reboot)
sudo bash tools/local/lo0-alias.sh

# 2. static config server
cd tools/local && python3 -m http.server 8080 --bind 127.0.0.1 &

# 3. game server  (JDK 21) -- build once, then run standalone
JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home \
  ./gradlew :server:app:installDist --console=plain
JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home \
  JAVA_OPTS="-Xms256m -Xmx2g" ./server/app/build/install/app/bin/app

# 4. RSProx GUI  (separate repo, JDK 11 toolchain)
cd ../rsprox && JAVA_HOME=/opt/homebrew/opt/openjdk@21/libexec/openjdk.jdk/Contents/Home \
  ./gradlew proxy --console=plain
```

In the RSProx window: Jagex Account Mode `Default`, client `RuneLite`,
target `RS Mod (local)`, then **Launch**. Log in with any username/password —
the dev realm has `ignorePasswords=true` and `requireRegistration=false`.

### Memory

`./gradlew run` holds a Gradle daemon (~300 MB) *alongside* the server JVM it forks, and
RSProx adds a second daemon for its own Gradle version. Stacked with Kotlin compile daemons
from earlier builds, macOS starts killing processes. Two habits avoid it:

- Run the server from `installDist` (above) instead of `./gradlew run`, so no daemon is held
  while playing. Rebuild only after code changes.
- `./gradlew --stop` in *both* repos after a build session; different Gradle versions keep
  separate daemons, so stopping one does not stop the other.
- Cap the server heap with `JAVA_OPTS="-Xms256m -Xmx2g"`. The start script ships
  `-Xms1g` and the JVM default max is a quarter of RAM (4 GB on a 16 GB Mac). RSMod holds
  the cache and map resident, so it settles around 1.4-1.9 GB; 2 GB is enough and stops it
  ballooning. Check with `ps -eo rss,args | grep install/app`.
- On a 16 GB Mac with a browser and chat apps open, total RSS sits near 11 GB and swap runs
  hot; the server is the process macOS reaches for first. `sysctl vm.swapusage` is the
  honest signal — "memory free percentage" stays optimistic while swap is exhausted.

## Toolchains

Two JDKs are required and Homebrew's keg path is *not* a valid `JAVA_HOME` —
the real one is nested under `libexec`. Both are registered in
`~/.gradle/gradle.properties` via `org.gradle.java.installations.paths`.

| | |
|---|---|
| RSMod | JDK 21 (`jvmToolchain(21)`, Gradle 9.0) |
| RSProx | JDK 11 (`jvmToolchain(11)`, Gradle 8.7) |

## Files here

- `jav_config.ws` — built from the genuine OSRS config, overriding only
  `codebase`, `param=25` (revision 233), `param=17` (world list) and
  `param=12` (initial world). The client reads ~23 applet params at startup and
  NPEs in `client.init()` if they are missing, so do not hand-write a minimal one.
- `worldlist.ws` — binary, generated by `make_worldlist.py`. Its `host` field
  must equal the `codebase` host in `jav_config.ws`; RSProx does a
  `checkNotNull` lookup on that and will fail to launch otherwise.
- `lo0-alias.sh` — adds/removes the `127.0.1.3` alias (`remove` to undo).

## Gotchas

- **RSProx caches `jav_config` at target load.** After editing it, restart
  RSProx — pressing Launch again is not enough.
- The genuine OSRS `jav_config.ws` uses **CR-only line endings**, so `grep`
  sees one line. `make` scripts here normalise to LF.
- RSProx serves the config wrapped as `JavConfig(text=…)`. Harmless — RuneLite's
  parser skips lines without `=`.
- The port RSMod binds is set by `port` in `.data/server.toml` (default 43594).
- **A content change that dirties the cache makes `*:integration` tests hang forever.**
  `GameServer.verifyTypeResolver` handles "cache needs repacking" by repacking and then
  calling `startApplication()` recursively — which includes `startupGame()`. Under
  `./gradlew run` that is the intended restart. But `GameTestState` only calls
  `prepareGame()`, so the recursive restart escapes the harness, binds 43595 and blocks in
  `ServiceManager.awaitShutdown`. The test never fails, it just never returns.
  **Run `./gradlew run` once after changing configs/refs** so the repack happens there, then
  run the tests. If a test run sits at 0% CPU, check `lsof -nP -iTCP:43595 -sTCP:LISTEN` —
  a listening test JVM is the tell.

## Our content

Custom content lives in `content/custom/*`. Nothing needs registering: Gradle
walks `content/` for any directory with a `build.gradle.kts`, `server/shared`
depends on every one it finds, and classgraph scans `org.rsmod.content` for
`PluginScript`/`PluginModule`. Watch the boot log's script count to confirm a new
module loaded.

- `content/custom/drop-tables` — npc drop tables for the Lumbridge starter npcs
  (chicken, cow, rat, giant rat, man/woman, goblin). Weights are the official
  `/128` tables and the builder asserts each table sums to its denominator, so a
  typo fails at boot instead of quietly skewing drops.
- `content/custom/city-shops` — stock and shopkeeper wiring for the Al Kharid and
  Varrock shops, plus general stores 2–7. Vanilla `.inv` types carry only a `size`
  (stock is an RSMod extension, codes 200–205), so a shop with no `InvEditor` entry
  opens completely empty — which is why every shop needs its contents written out.
  **Known gap: none of these shopkeepers actually spawn** (see the npc-spawn gotcha
  below). The stock and op wiring are correct and tested; the npcs are not in the world.
- `content/custom/barrows` — the Barrows minigame: dig a mound with a spade, search a sarcophagus to
  raise its brother, and loot the chest at the centre of the crypt. **The tunnels are not in this
  cache.** A whole-map scan finds no barrows door, ladder, chest or rockslide placed anywhere, and
  level 0 of mapsquare 55_151 - where OSRS puts the maze - has no locs and not one walkable tile.
  What does exist is level 3: one connected crypt complex holding all six sarcophagi and all six
  staircases, which serves as the tunnels here, so the reward chest is spawned by us at its centre.
  The brothers are already statted in the cache (levels, bonuses, attack speed); what
  `BarrowsNpcEditor` adds is `attack_melee`, ranged defence, an attack type, attack animations and
  the aggression they otherwise lack. Ahrim and Karil have hand-rolled ranged and magic attacks
  because `NvPCombat` only ever builds a melee one. `api/cache/.../BarrowsDump.kt` re-prints all of
  it against the installed cache.
- `content/skills/mining` — the full ore ladder (clay through amethyst plus runite),
  the pickaxe ladder, rock depletion and fixed-timer respawn. Gem rocks are
  deliberately absent: they roll a weighted gem table rather than one fixed product.
- `content/skills/firemaking` — tinderbox on logs, twelve log tiers, fire loc with a
  per-log burn duration that collapses into ashes on the same tile.
- `content/skills/smithing` — smelting at a furnace and smithing at an anvil. The anvil half
  drives the game's own interface (312) and reads its numbers out of the cache's enums, so
  only the button→product mapping is authored here. The furnace opens the vanilla make-menu
  (`skillmulti`, interface 270), whose undocumented arguments were decompiled out of the
  cache — see the clientscript gotcha below. Using an ore on the furnace still works as a
  shortcut.
- `content/skills/fishing` — all five spot archetypes (net/bait, lure/bait, cage/harpoon,
  big net/harpoon, and Tutorial Island's net-only spot), shrimps through shark. Spots are
  **npcs**, so the loop re-queues `opNpc1`/`opNpc3`; and a spot never depletes, so a catch
  keeps the loop going. Which method an op runs is read from the spot's own cache ops rather
  than configured per spot — see the op-pair gotcha below. **Known gap:** OSRS spots relocate
  on a timer and ours stand still, which makes fishing slightly *better* than live.

- `content/skills/magic/magic-*` — the spellbooks beyond upstream's twenty elemental spells,
  built 2026-09-09. `magic-commons` holds what the rest share: the spell reader (`MagicSpellbooks`,
  a second reader of the cache enums because upstream's registry cannot list a book and is
  populated by a Guice provider the test harness never installs), rune payment with xp through
  `XpModifiers`, freezing on the engine's `frozen` walk trigger, and `MagicRuneTestSupport` for
  tests. `magic-spellbooks` binds every teleport that carries a `spell_telecoord`, places the
  Ancient and astral altars in the square north of the Edgeville bank at boot (ungated: there are no
  quests), adds `::spellbook 0|1|2` and Lunar Spellbook Swap. `magic-utility-spells` is alchemy,
  Superheat, Bones to Bananas/Peaches, the seven jewellery enchantments (authored: dbtable 86
  `magic_enchant` has names but no data in this cache), charge orbs, Charge, Vengeance and the Lunar
  inventory spells. `magic-combat-spells` registers the curses, binds, god spells, Iban Blast,
  Magic Dart, Crumble Undead and all sixteen Ancient Magicks as `SpellAttack`s. Deliberately out:
  Arceuus, Telekinetic Grab (the `OpObjT` packet is a no-op upstream), every player-targeted
  spell, and poison (smoke spells only deal damage). The enchant sub-list opens client-side: its
  `magic_spellbook_op` clientscript sets varbit `spellbook_sublist` locally, so the server only ever
  sees the `enchant_N` buttons.

## Sharing this checkout with another agent

Two Claude Code sessions worked in this tree at once on 2026-09-08 and collided three ways.
Worth knowing before doing it again:

- **`.data/symbols/.local/*.sym` ids clash.** Both sessions picked the next free id in the same
  file. `NameLoader` *does* catch duplicates within one file, so this fails at boot rather than
  aliasing — but only after you have written the code. Check the file immediately before
  appending, and leave a gap.
- **Concurrent Gradle builds corrupt each other's caches**, failing with
  `Could not pack tree 'classpathSnapshotProperties.classpathSnapshotDir'` on unrelated modules.
  Retrying usually clears it; `--no-build-cache` sidesteps it.
- **One port, one server.** Integration tests and the dev server both want 43595, and a test JVM
  that escapes via the repack path (below) holds it until killed. `lsof -nP -iTCP:43595
  -sTCP:LISTEN`, then check the pid's `-Dorg.gradle.internal.worker.tmpdir` to see whose it is.
- Any module that does not compile blocks the *other* session's integration tests too, since
  those build the whole server. Separate git worktrees would remove all of this.

## Gotchas when adding content modules

- **Npc spawns are authored by us, not read from the cache.** `MapNpcListEncoder` notes
  that map npc spawns are "a server-only group": the vanilla cache carries none, and
  RSMod packs them from `MapNpcSpawnBuilder` content. The *only* spawn builder upstream
  ships is `LumbridgeNpcSpawns`, whose `npcs.toml` covers 585 spawns across mapsquares
  49–50 × 49–51. Everywhere else in the world is empty of npcs. Al Kharid (51_49) and
  Varrock (50_53) are outside that box, which is why the `city-shops` shopkeepers have
  correct data and still cannot be found in game. Adding npcs to a new town means writing
  a `MapNpcSpawnBuilder` and a `npcs.toml` of coords — a type-level test will not catch
  the omission, because the types resolve fine.
- **Cooking and fishing are empty stubs.** `content/skills/cooking` and
  `content/skills/fishing` contain a `build.gradle.kts` and no source at all. The only
  skills with a real implementation upstream are woodcutting and magic (spell attacks).
- **Our own symbols live in `.data/symbols/.local/`.** `SymbolModule.shallowSymbolDirectories`
  merges `symbols/` and `symbols/.local/`, so new content groups, params and enums go in
  the latter and never conflict on rebase. The stock `.data/.gitignore` drops `.local/`,
  which would break a fresh clone, so it is explicitly un-ignored. **Id allocation matters:**
  `NameLoader` only rejects duplicate ids *within one file*, so an id shared with upstream
  silently aliases two different types. Vanilla grows upward (params to ~1935, enums to
  ~4956) and RSMod's own additions count *downward* from 65534; ours start at 50000 in the
  gap between them.
- **`ProtectedAccess.mapClock` is an `Int`, and it shadows an injected `MapClock`.**
  Inside any `ProtectedAccess` extension function, a constructor-injected `mapClock`
  is invisible — the receiver's `Int` wins, and the failure is an unhelpful "none of the
  following candidates is applicable" at the call site. Upstream relies on this shadowing
  deliberately (`actionDelay < mapClock`). Name the injected field something else.
- **Interfaces can tell you how to drive them — read the cache, don't guess.** A component's
  `onLoad`/`onOp`/`onVarTransmit` arrays and a clientscript's `switches` table are all decoded
  into `TypeListMap` and dumpable from a throwaway `GameTestState` test. That is how the
  smithing interface was settled: component 0 of interface 312 carries
  `onLoad=[clientscript,smithing_init]`, so it initialises itself, and `proc,smithing_setup`
  switches on varp `smithbars` with **bar object ids** as the keys (`bronze_bar(2349)` …
  `runite_bar(2363)`, plus `lovakite_bar`). Server side is therefore just "store the bar id in
  the varp and open the interface". `UnpackedClientScriptType.intArgumentCount` gives a
  script's arity for free, and `commands`/`intOperands`/`stringOperands` give the whole opcode
  stream — you can read an undocumented signature straight off it. That is how the make-menu
  was recovered: `clientscript,skillmulti_setup` advertises only "13 ints + 1 string", but its
  body tests args 3..11 against -1 to count buttons (so 2..11 are ten item slots), clamps arg 1
  into 1..28 and uses it as the ceiling for arg 12 (max quantity, then starting quantity), and
  uses arg 0 solely as a key into enums 1809/5178/1810 (the verb, and which quantity buttons
  appear). `api/cache/.../SkillMultiDump.kt` re-prints all of it against the installed cache.
- **A menu's chosen quantity arrives as the button's *subcomponent*, not as an op.** The
  make-menu's item buttons carry no static events in the cache, so nothing reaches the server
  until you call `if_setevents` on them — and `proc,skillmulti_itembutton_triggered` re-targets
  the button at the selected quantity before firing it, exactly the way the chatbox option menu
  carries its option index. So enable the op over the whole `0..28` subcomponent range and read
  `IfModalButton.comsub` as the count. `InterfaceEvents.isEnabled` treats `comsub == -1` as
  "check the cache's static events", which for these components would reject everything.
- **Loc ops are *still* not uniform, and plenty of locs have none.** Anvils carry `Smith` on
  **op1** but furnaces carry `Smelt` on **op2**, and Tutorial Island's `newbiefurnace` carries
  `Use` on op1. `gim_anvil`, `gh_anvil`, `wint_anvil`, `furnace2`, `bcs_furnace`,
  `viking_furnace2` and `dwarf_keldagrim_furnace2` are decorative twins with no ops at all —
  binding to them silently does nothing. Dump `loc.op` before writing the binding.
- **Type edits are additive once packed; you cannot untag a type by deleting the edit.**
  Removing a `contentGroup` line from a `LocEditor`/`ObjEditor` leaves the old value sitting in
  `.data/cache/game`, and no repack reverts it — the resolver only notices types you *declare*.
  A fresh clone would then build a different world than the machine you tested on. If a tag was
  ever packed, keep it listed (with a comment) rather than silently diverging.
- **Integration test *methods* run in parallel and share one game world.**
  `integration-test-suite` sets `junit.jupiter.execution.parallel.mode.default=concurrent`
  (classes are `same_thread`, methods are not). Two methods that place a loc on the same tile or
  move items around race each other, and it shows up as items surviving a transaction that
  clearly ran, or as a bare `ConcurrentModificationException` — on maybe one run in three.
  Put `@Execution(ExecutionMode.SAME_THREAD)` on any suite that mutates world or player state.
  Note `--rerun` is needed to actually re-execute a green test task; without it Gradle reports
  success having run nothing.
- **An open modal makes a player access-protected, so tests cannot click one.**
  `Player.isBusy` is `isDelayed || ui.modals.isNotEmpty()`, and `isAccessProtected` builds on it.
  Production dispatches modal buttons with `ProtectedAccessLauncher.launchLenient`, which
  bypasses that check; the test harness only exposes the strict `launch` via
  `player.withProtectedAccess`, which silently does nothing while a modal is open. Test the
  opening and the button press as two separate cases, setting any varp the handler needs from
  inside a `withProtectedAccess` block while the player is idle.
- **The test harness clears its message buffer every tick.** `assertMessageSent` reads
  only what was sent during the most recent `advance`, so an assertion has to land on the
  same tick as the message. A check that rejects synchronously must be asserted with no
  `advance` at all.

- **A content module cannot share its directory name with any other Gradle project.**
  `settings.gradle.kts` includes projects by path but Gradle still takes the *name*
  from the last path segment, so `content/custom/shops` collides with `api/shops` and
  fails with a self-referential `Circular dependency between :content:custom:shops:classes`
  and `:jar`. The error never mentions the collision. Prefix the directory
  (`city-shops`) instead.
- **Don't guess which right-click slot an npc op lives in.** It is not uniform: the
  shopkeepers here all carry `Talk-to` on op1 and `Trade` on op3, but Bob has `Repair`
  on op4, and Aubury has `Teleport` on op4 in one of his two variants. Decode it — a
  throwaway `GameTestState` test that walks `cacheTypes.npcs` and prints `npc.op` costs
  about a minute and settles it. Some named npcs (`aubury`, `thessalia`) are nameless
  placeholder types with no ops at all; the types that actually spawn are the variants
  (`aubury_2op`, `aubury_3op`, `thessalia_normal`).
- **Sometimes the op *pair* is the data, and a single op is ambiguous.** Fishing spots are the
  clean example: all 92 standard ones carry their two methods on **op1 and op3**, never op2, and
  op1 alone cannot tell you what the spot is — `Net` means a small net when op3 is `Bait` and a
  big net when op3 is `Harpoon`. `content/skills/fishing` therefore dispatches on the pair, which
  is also what the player reads. Where the cache already states something this exactly, prefer
  reading it over inventing params or content groups to restate it: the tagging cannot drift out
  of step with the cache, and there is nothing per-spot to get wrong. A content group is still
  needed as the hook (`onOpNpc1` needs *something* to bind to), but it carries no meaning beyond
  "this is a fishing spot".

## Changes to upstream RSMod

Kept deliberately small so rebases stay cheap:

- `api/server-config/.../ServerConfig.kt` — added `port` (default 43594)
- `api/net/.../NetworkFactory.kt` — binds `serverConfig.port` instead of a literal
- `api/player/.../hit/processor/StandardPlayerHitProcessor.kt` — publishes `PlayerHitEvents.Impact` after
  a hit lands, so Vengeance (and any future recoil effect) can react without owning the hit queue
- `api/testing/.../scope/GameTestScope.kt` — `opNpcT`, `opLocT` and `ifButtonT` helpers for spell targets
